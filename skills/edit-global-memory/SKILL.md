# Edit Global Memory

## When to apply

Apply the latest explicit direct-work, no-delegation, and skill-nonuse instructions before selecting this workflow or its default owner. A direct-work instruction assigns the current work to that agent; it does not abolish normal delegation or change the standing model/effort settings. If this skill is prohibited, do not invoke its ownership workflow. Reading this skill as the artifact under inspection does not itself activate that workflow. The ownership rules below are defaults when the user has not specified a different execution method.

Classify the latest message in this order, before applying the read-only exclusion:

1. Check whether it continues an authorized memory/skill improvement or durable behavioral correction. A problem definition, a report that an existing rule was not followed, or a challenge to a claimed repair continues that work even without another edit command. A prior completion report, completed original task, existing rule coverage, or interrogative wording does not make it a standalone explanation request. Before stopping or changing scope, compare the latest correction with the preceding request, assistant interpretation, and actual action. Distinguish rejection of a proposed rule or narrow interpretation from cancellation of the improvement itself; withdraw only the rejected part and continue the authorized repair unless cancellation is explicit. Carry the correction into the parent's source-and-decision audit below; do not choose “no action” before that audit. This authorizes finding and repairing the failed decision within the existing scope, not adding a new policy by default.
2. Otherwise, use this skill for an explicit request to improve, compress, remember, or update global memory, or a durable correction to cross-task behavior or preferences established by the conversation. Do not require the skill name, file path, word “memory,” or a particular phrase such as “never again.” Repeated editing requests are a fresh audit even when a prior update exists.
3. Only when neither condition applies, treat a request only to read, reread, inspect, confirm, quote, or explain memory or an event as read-only. The parent reads the permitted source directly without invoking this editing workflow or launching an editing owner. Standalone criticism or questions do not authorize inventing a broader policy.

Determine the correction's scope from the user's words and surrounding exchange. Before classifying it as a one-off task fix, compare the chosen actions and unattended outcomes with the request and existing rules; do not wait for the user to label the mismatch an error or request memory editing. Criticism or interrogative wording does not skip this assessment. Distinguish correction of an artifact from correction of the behavior that produced it, without treating criticism alone as permission for unrelated policy. Failure transcripts and thread links supplied during improvement work are evidence. Identify task execution, improvement recognition, and corrective execution failures separately; treat listed symptoms as evidence to trace their shared cause and affected scope, not an exhaustive edit boundary. An instruction to include a cause adds it to the cumulative repair; it does not replace that repair. A request to keep future answers in polite Japanese is a global preference; a request to fix this document's wording is a local edit. “Improve this” can be a durable correction when it refers to recurring assistant behavior. Preserve that scope through the audit below.

The parent reads the rule, procedure, and original exchange without launching an editing owner or an additional high-cost reader. Decide coverage and execution failure separately:

| Finding | Required action |
|---|---|
| An independent requirement is missing | Identify its governing source and the missing requirement evidenced by the original exchange; assign the verified editing owner below. |
| The rule exists but was not followed | Identify the bypassed decision and select its next authorized corrective operation from the original evidence. If a governing-procedure edit is needed, dispatch the verified editing owner below; otherwise perform the already-required operation. Inspect the resulting diff or execution evidence before closing this branch. A coverage finding is not a completed correction. |
| Neither a missing condition nor an execution failure remains | Substantiate it against the original case and finish remaining authorized work. |

Before dispatch, identify the observed failure or missing requirement and the user’s requested outcome; leave the repair method and wording to the editing owner. No textual edit means only no textual edit: diagnosis, withdrawal of a claim, or naming a repair target does not execute an outstanding correction. Do not replace the requested improvement with a requirement to guarantee all future behavior. A failure in this skill requires repairing this skill in the same request; stopping its worker or acknowledging it is insufficient.

Keep an explicit global-memory request global; skill/project-only changes stay there. Standalone capability questions or quoted instructions remain read-only, while their use in continuing improvement follows step 1 above. Judge improvement by corrected behavior and results, not more text or checks. Apply the latest retention contract and the permanent 20,000-byte UTF-8 cap; a larger Codex loading limit does not authorize growth. Distinguish requirements the user specially designates as mandatory from ordinary corrections and consolidation: place them in the final `## 8. 本人指定の必須要件` section of AGENTS.md, which is excluded from the cap and may exceed 20,000 bytes. Ordinary corrections stay within the cap and must not be moved into that section to avoid it. The editing procedure below defines the protected behavior, scope review, and size checks.

The native GPT model requirement applies to the editing owner, not the coordinating parent. A non-GPT parent (including Claude routed through opencodex) performs the read-only assessment and delegates the concrete edit to one verified GPT-6 Astra subagent with reasoning effort `low`, following the ownership and lossless-handoff rules below. A provider delivery error such as "Routed V2 worker task is encrypted for the native ChatGPT backend and cannot be read by the selected provider" means the parent cannot read that message; it does not prohibit delegation or prove that editing failed. Do not interpret unreadable messages. Verify the owner’s work through the actual file diff, validation evidence, and Git commit, compared with the original conversation. The owner commits only its intended changes with a descriptive Japanese message, preserving pre-existing differences. If completion or validation cannot be established from those artifacts, recover the missing evidence from the same owner rather than requesting another task or duplicating the edit.

This skill specifies the editing model, ownership, delegation, source handoff, and acceptance procedure. Apply those steps directly; do not add `codex-work-orchestration` as a required handoff stage merely because an editing owner is delegated. Read applicable [delegation defaults](../codex-work-orchestration/references/user-work-preferences.md) directly; this is not an additional execution workflow. Use orchestration only for a separate coordination need not already covered here, and identify that need before adding it. If this selection is challenged, correct the added workflow itself rather than treating the error as merely unclear wording.

Write corrective rules as concise, natural instructions that guide the failed decision. Keep the relevant purpose, permission boundary, trigger, action, and completion evidence connected, without requiring a fixed set of fields or repeating what the governing text already establishes. Where a prohibition would otherwise leave the next action unclear, state the permitted path grounded in the user’s instructions and verified facts. This writing guidance does not expand authority or replace privacy and truthfulness conditions. Validate the wording against the original case and applicable exceptions; a preferred sentence structure is not evidence of effectiveness.

## Select the responsible model

Resolve the explicit execution instructions above first. Otherwise use the unchanged model and delegation defaults in this section. A directly assigned owner follows the same source, scope, editing, and validation requirements; references to the top-model owner in the procedure describe the default route, not a reason to override that direct assignment.

Once a concrete edit is needed, the current top model owns the edit’s semantic decisions, retention/removal decisions, drafting, canonical edits, and final validation. Parent status alone never qualifies an agent for editing ownership. Do not dispatch the top model merely to read or decide whether an edit is needed; the parent performs that preliminary work.

Use the user's latest explicit top-model designation. As of the user's 2026-09-05 instruction, that designation is GPT-6 Astra (`gpt-6-astra`), replacing the former Sol designation. This is a dated user preference, not a permanent ranking: follow a later explicit designation, or verify current authoritative model information and runtime availability when the designation needs updating. Never infer rank from list order, a default model, or the strongest model exposed by a restricted subagent tool.

- The user’s standing default is one delegated editing owner within this task, even when the parent is the designated top model. Do not replace required delegation with direct parent edits or a separate thread. The delegated owner performs the work itself; this rule does not require recursive delegation. After dispatch, the parent proceeds with authorized work that does not depend on the edit. Before waiting, identify the concrete result or resource the next operation requires; the worker being active or a possible connection interruption alone is not a dependency. Handle any actual shared-process interruption through its authorized recovery path, without making the edit’s completion a prerequisite for independent work.
- If the parent is Luna or any other lower-tier model, delegate the concrete editing and validation workstream to one verified top-model owner after the parent identifies the required edit. This standing user instruction authorizes that editing delegation; do not ask again. Per the user’s 2026-09-16 clarification, delegation required for global-memory editing is exempt from the general requirement to obtain explicit permission for high-cost subagent models. The exemption covers only this memory-editing workstream, not other work in the same task. A top-model parent follows the same delegation default unless the user explicitly assigns direct ownership.
- Here, “delegate” means assign the work to a subagent within the current workstream. It does not mean creating a new Codex task, opening a separate user-visible thread, or moving the work out of the current task. Do not create or suggest a new task merely to satisfy this delegation requirement.
- For global-memory editing, use Astra with reasoning effort `low` only. Explicitly set `low` when delegating and verify the actual model and effort before editing. `medium`, `high`, `xhigh`, `max`, and `ultra` are prohibited for this work; a prohibition on `high` does not permit any higher effort. Neither the top-model designation nor the high-cost-model exemption authorizes increasing effort.
- Use only a route that supports the exact selected model and confirms its actual execution model. Do not send an unsupported model identifier or silently substitute Sol/Luna because the current spawn surface lacks the top model. If no authorized route can run the top model, leave the canonical memory unchanged and report the specific blocker.

Keep one editing owner. Follow the user's explicit ownership instruction, including delegation when the user requires another agent to edit. A lower-tier parent coordinates the request and returns the top owner's evidence; it does not rewrite or semantically override that owner's result. The parent supplies the affected source, the observed mismatch that requires repair, and the user’s original scope and evidence. Do not put the parent’s diagnosis, proposed wording, or preferred remedy into the owner’s task instructions, even with a “proposal” or “judge independently” label. Preserve earlier assistant diagnoses in the original conversation as actions to audit, not as a prescribed repair. The editing owner derives the correction from that source evidence. Before delegation, provide the relevant conversation in its original wording and order: the user's request and every correction, the assistant replies and actions they refer to, and the tool results needed to assess those actions. Preserve the requested scope and surrounding context. A collection of user messages alone, a parent summary, interpretation, or narrowed restatement is not a substitute. Full-history inheritance or a readable original transcript can provide this context; verify what the owner actually received. If required context is missing, retrieve it before semantic editing. Send subsequent corrections to the same owner with their context.

The lossless handoff happens before editing, not as a repair after an edit. Do not edit from a compressed request and then report what was omitted or added. The owner reads the supplied source context before deciding what to retain, add, or remove, and the parent checks the completed diff against that same source context before reporting completion. This check validates the result; it must not be used to recover intent that was withheld during handoff.

## Low-cost assistance within global-memory work

The restrictions in this section apply only to editing global memory. They do not restrict Luna or other subagents from implementation, editing, or artifact production in other authorized work; the parent audits those completed results under AGENTS.md, using `codex-work-orchestration` only when actual coordination is needed.

The parent normally reads source text, inventories relevant files, inspects history, and decides whether a concrete edit is needed. Use a bounded low-cost retrieval agent only when it materially helps; do not launch an additional high-cost retrieval agent for this preliminary stage. Preserve source locations, original wording and context, and uncertainty. Preliminary assessment does not authorize the parent to draft or apply canonical edits, choose removals, or accept the final edit in place of the designated editing owner.

The top-model owner reads [the editing procedure](references/memory-editor-procedure.md). Preserve the current request and corrections over older local workflow rules. Durable corrections belong in their governing source: global behavior here, specialized behavior in its skill or project. Continue independent original-task work during the repair; integrate the owner’s result when it arrives.
