# Global memory editing procedure

The parent first performs the read-only assessment in SKILL.md and identifies a concrete edit target. Apply the latest explicit direct-work, no-delegation, or skill-nonuse instruction before the default ownership route. Otherwise the verified top-model owner performs the edit. The selected owner follows the same source, scope, and validation requirements below. Do not launch an editing owner for reading alone.

1. Read the current `~/.codex/AGENTS.md` and the original conversation supplied under SKILL.md, including the assistant replies, actions, and relevant results that explain the user's corrections. Confirm receipt of that context before editing; user-only extracts and parent summaries are insufficient. If context is missing, retrieve it without inferring the missing intent. Separate the user’s original requirements and observed actions from the parent’s interpretation. For delegated edits, check the actual delegation message before drafting for a diagnosis or remedy presented as editing direction; a “proposal” label does not make it a requirement. If present, discard that direction, assess the original exchange independently, and review any affected draft against the original evidence. Continue with the same owner; do not request another handoff when the complete source is already available. Include this delegation failure in the skill repair rather than closing it with a re-review of AGENTS.md alone. When the correction concerns this skill’s reading, delegation, or editing decisions, repair the relevant skill procedure in the same workstream. Stopping a worker, acknowledging the correction, or changing AGENTS.md alone does not resolve that failure. Preserve permitted independent work while carrying the concrete edit through validation. Inspect existing differences before editing. Treat a repeated improvement request as a fresh audit of the current content. When a correction identifies an unauthorized interpretation, inspect both the resulting action and the decision that treated that interpretation as permitted. Do not classify the correction as only a future preference and stop after acknowledging it. Within an existing improvement request, map the interpretation failure and any failure to recognize or execute its repair to the governing procedure before drafting the response. Preserve the general decision principle rather than adding a prohibition that merely names the reported incident. For a specified restart or restoration, verify the designated source in Git and rebuild from that point, preserving unrelated changes and later authorized corrections; do not substitute a failed intermediate draft. Do not read `~/.codex/memories/MEMORY.md`.
2. Build the current acceptance criteria from the original wording and cumulative corrections before drafting. Preserve the performance of responses, correction and verification, permission handling and user burden, apology, continuity, and completing authorized requests through obstacles. These are behavioral requirements, not fixed text lengths or verbatim wording. Preserve other existing conditions by default; when the user explicitly authorizes selection or removal, record that scope and do not reimpose full retention. Do not generalize one authorized removal into a standing permission to delete unrelated requirements. Before announcing an interpretation or drafting a rule, trace each proposed condition to the original request and cumulative corrections, and compare the breadth of the proposed repair with the requested improvement. When the editing decision depends on Codex instruction behavior, check the relevant implementation and Codex/AGENTS.md-specific official documentation before editing; reuse verified evidence only when its conditions still match. Assess each source’s applicability to the target and decision, not official status alone. Separate documented behavior, editorial inference, and unresolved points; generic writing advice, general model rules, and loading checks do not establish behavioral equivalence. If a correction rejects your interpretation, revise that interpretation while retaining the authorized edit; do not substitute a narrower incident-specific rule, an inferred motive, or a declaration that the rejected condition will be omitted. Select and execute the source-backed edit, then validate its result. Preserve specific user choices, approval boundaries, requested scope, and useful failure recovery. Do not add conditions, restrictions, or goals the user did not state, and do not narrow a rule by inserting a time, turn, target, or other qualifier unless the user did so. Merge repeated rules while preserving their required decisions and response conditions. Rewrite sentences and structure where useful; do not limit compression to suffix deletion or repeated words. A decomposition into fields is an editing aid, not proof: preserve how triggers, obligations, permissions, priority, timing, exceptions, evidence, and response constraints connect. Preserve the prerequisite, evidence, scope, and recovery action of a conditional rule together; do not replace a condition for claiming success or prevention with a general duty to improve or an unconditional promise. For compression or loss audits, compare the complete before/after text. For each affected condition, record its retained meaning and location, superseding instruction, explicitly authorized removal, or unapproved loss. Restore unapproved losses; do not restore a condition the user authorized removing merely to satisfy an older full-retention rule. Review text-only compression separately from authorized behavioral changes. Compare later amendments with those conditions, not just the compressed version. Remove obsolete or excessive workflow requirements only with a reason grounded in the request. Choose the editing operation before drafting: locate the governing condition and its overlaps, then consider rewriting that clause, merging overlapping conditions, removing redundant or superseded wording, and placing specialized detail in an applicable existing skill only when that relocation is separately authorized. Preserve the retention mapping required above. Add a clause only when those edits cannot express a source-backed independent missing condition. Existing-rule violations require repair of the failed decision, not a synonymous rule or incident example. Record the chosen operation and why it fits the source requirement for the final diff review. Before choosing the editing destination, distinguish a current-task instruction from an explicitly established cross-task preference using the original exchange. Inspect the existing governing skill before deciding that operational detail belongs in global memory; a concrete path, date, or current placement is not by itself a durable default. Keep global instructions to durable user choices and decision boundaries. Retain task-specific facts in their project source and reusable specialized procedures in the applicable existing skill, without inventing a broader rule merely to move it out of global memory. Read specialized procedures only when applicable. Byte reduction alone does not prove quality. Do not satisfy the memory cap by moving instructions into another file; any separately authorized relocation is not compression. Before deleting or generalizing an existing rule, identify its explicit prohibitions, required wording, and independent conditions. Locate each protected requirement in the result; for an authorized removal, identify the instruction and scope that permit it instead of inventing a retention location. A general style instruction is not a replacement for a specific prohibition or wording preference: avoiding repetitive apologies does not revoke a prohibited phrase or an explicitly preferred form. Remove or change such a condition only when a later user instruction actually authorizes that change; cite that instruction, not an inferred stylistic intent. If that evidence is absent, retain the condition. Apply this comparison to every changed clause of a disputed commit and preserve unrelated valid changes and subsequent corrections when repairing it.
   When an existing rule was ignored, inspect both the violating decision and whether the rule supplied an effective instruction at that point. Locate what was requested, what was authorized, which condition the assistant introduced or removed, and the resulting change in scope from the original exchange and actual operations. Correct an unauthorized condition by withdrawing it and restoring the requested scope, preserving real exceptions; do not replace that repair with a new restriction, a narrower incident rule, or a general request for more comparisons. Repair the governing decision procedure if it selected or excused that unauthorized change. Assess whether the existing wording actually guides the failed decision; its presence is not evidence that it suffices. When the user identifies an unenforced rule as inadequate and requests a global-memory repair, rewrite that governing rule into an actionable decision with a check before the failed action. Preserve its scope and exceptions, and repair any editing procedure that excluded this work merely because the rule already existed. Trace selected conditions to the user's words, actual workflow requirements, or higher-priority requirements, not to the assistant's chosen example, identifier, or intermediate artifact. Check the corrected decision with incidental identifiers changed but authorized conditions held constant, and with a genuinely limited instruction that must remain limited. Re-evaluate the observed case through a concrete next operation, preserving permission boundaries and ownership. Execute the permitted discovery and checks needed for that choice; identify the actual target, input, operation, and result. A plan to check later or merely excluding the failed choice is insufficient. Reuse verified completed work rather than repeating writes or another owner's task. This procedural verification does not establish that the original project is repaired or authorize taking over another thread's work.
   When the user supplies a failure transcript or thread link during a memory/skill improvement discussion, assess it as evidence for that improvement rather than ending at “the rule already exists.” Determine whether the problem is missing content, a bypassed execution/termination decision, or both. Trace the exchange from the earliest correction, identifying when the available evidence first required auditing the failed decision under AGENTS.md, when that audit actually began, and what the assistant did in between. Assess the original task failure, delayed recognition of the improvement target, and delayed corrective execution separately. A later explicit editing request or completed artifact repair does not excuse an earlier missed trigger. For each evidenced failure, identify the bypassed decision, execute its authorized correction, and inspect the result before closing the audit; do not accept a repair of only the original task behavior as completion of the other failures. Inspect the procedure actually used at that decision and repair the concrete gap within the existing authorization. A read-only explanation request alone remains read-only. Preserve the other thread’s ownership: reading the supplied evidence does not authorize messaging it or duplicating its task. Validate the changed procedure against the observed sequence, identifying the next permitted operation and evidence required before termination; distinguish this procedural check from a successful rerun of the external task.
3. The selected editing owner reviews the source wording and proposed differences, then writes the update. Read-only subagents may retrieve evidence; their recommendations do not authorize edits. Preserve concurrent changes. If Git does not contain the baseline, retain the actual pre-edit content before overwriting it. Do not edit from a lossy summary and discover omitted intent afterward. Read the original context before editing; a delegated owner must receive the lossless source handoff first.
4. Compare the final diff with the source wording, retained conditions, and editing operation chosen in step 2. Verify the actual rewrite, merge, removal, move, or addition repairs the identified decision. Remove redundant examples and reject additions that existing wording can absorb. Check omissions, unsupported changes, narrowed scope, contradictions, and references. This review does not replace the pre-edit source handoff. Exercise affected cases and relevant non-applicable cases: an ordinary answer, an authorized action, a correction or short choice during unfinished work, and any specified route. Test both required continuation and cases where the work is already complete or the user forbids more work. Do not launch another model merely to approve prose. Use a separate model run only within its authorization. Distinguish source/meaning comparison, actual generated decisions and replies, loading checks, and real operation E2E. Do not call a hypothetical next-action answer an executed operation, or use keyword counts as functional proof. If before and after both pass, report that the test did not demonstrate improvement; neither a passing sample nor new wording guarantees future behavior.
   Apply the parent's SKILL.md decision table to each failure and inspect the action actually taken:
   - A needed source edit remains: complete and review it.
   - The text already suffices but the required correction is unexecuted: perform the authorized operation and inspect its result in this turn. Rule citation, recognition, claim withdrawal, a target statement, or an unfinished-work caveat cannot close this branch.
   - The correction was executed and checked: verify separately the repaired output and the decision that bypassed the existing rule. A compliant replacement reply proves only the output repair; before closing the decision repair, identify and correct the bypass in the governing procedure or its execution and inspect that result. Existing rule coverage does not discharge this check or require redundant rule additions. Report only the verified scope and continue remaining authorized work.
   Omit redundant rule edits without omitting required action. Test the branch against the original failed response: it must select the executable correction, not another explanation. Another thread's resumption does not finish this work, and repairing instructions here does not finish that thread's external task. Completion and genuine blockers follow step 6.
5. Run `python3 ~/.codex/skills/edit-global-memory/scripts/check_memory_size.py ~/.codex/AGENTS.md` before and after editing, and run `git diff --check`. The user’s permanent memory cap is 20,000 UTF-8 bytes, independent of Codex’s configured loading limit. The cap excludes the final AGENTS.md section whose heading contains `本人指定の必須要件`; place only requirements the user specially designates as mandatory there, and that section may exceed the cap. The checker and pre-commit hook count only the bytes before that heading. The checker permits only that cap or a stricter `--limit`. Keep the committed blob within the same cap enforced by `.githooks/pre-commit`; do not raise either limit or relocate instructions to bypass it. Compare the latest relevant Git baseline as well as the current diff to detect cumulative regrowth. Integrate and reduce existing wording rather than treating each correction as an append-only update or growth allowance. Use readable prose rather than cryptic symbol substitutions. Recheck the protected behavior after restructuring; the byte count is a separate acceptance condition.
6. Commit only intended changes under the repository's existing workflow. If automatic commit has already recorded the exact final content, verify that commit rather than creating a duplicate. Give the parent the actual diff and check results for comparison with the original conversation. Report only changes and checks supported by their execution evidence; a prior completion statement is not proof. Distinguish memory and skill repairs from project repairs: tests of project code do not validate memory edits, and memory checks do not establish project success. Return the before/after size, material behavior changes, validation, remaining limitations, and selected next operation to the parent as review evidence, without duplicating its work. Keep this evidence separate from the user-facing final response: follow AGENTS.md section 7, report the result in a few lines, and include detailed diffs, sizes, checks, or case walkthroughs only when requested. Do not forward the full evidence bundle as the final response. Before the parent closes the user turn, it checks remaining requested outcomes against actual results and existing permission, executes available authorized operations, and verifies their results. A completed memory edit or a promise to continue does not satisfy this task-completion check; stop only at completion or an evidenced blocker after permitted recovery.
